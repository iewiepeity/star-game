# 手機連續排程與原比例還原

基底：`dd0011c`；版本：核心 1.43.1／Pixel 0.20.1。

## 本次修改

- 行程畫面原本每次呼叫 `show()` 都執行 `panel.scrollTop = 0`。行程內更新改為保留捲動、鍵盤焦點及 `details` 展開狀態；排入活動時另保持同一張活動卡的位置。
- 活動卡取消按壓時的位移，避免連點時按鈕逐次偏離手指。
- 每次成功排入活動後接續下一個可調整日期。沿用排程助手的保護規則，略過正式通告、作客、城市邀約，以及已完成／進行中的日期。週末不繞回前面日期；仍可手動選日修改。
- 場景右上方與設定增加「回到原比例」。場景鏡頭回到當前螢幕的預設倍率並置中主角，城市地圖回到全市比例。
- 手機頁面放大後會另顯示浮動還原按鈕，依 `VisualViewport` 的範圍定位並補償倍率；開啟原生對話框時移到對話框內，保持可點。
- 還原頁面時短暫變更 viewport 的初始比例，再恢復原設定。保留玩家手動縮放能力，不重新載入頁面，不變更字體偏好或遊戲進度。
- 手機表單文字至少 16px，並固定文字自動調整的基準，減少輸入與旋轉螢幕造成的意外放大。

## 驗證範圍

結果：排程規則測試 1 項通過；手機瀏覽器 7 項通過、1 項因 WebKit 不提供 CDP 頁面倍率模擬而略過。修改檔案的 ESLint 與差異格式檢查通過。完整執行紀錄：[本次限定驗證](https://github.com/iewiepeity/star-game/actions/runs/34174720921)，驗證程式版本 `0444afc`。

首輪曾抓到活動卡按壓位移與 Chrome 未重新套用相同初始比例的問題；修正後，第二輪上述案例全部通過。測試過程使用的分支專用工作流程已移除，原有 CI 設定不變。

依本次要求，只執行修改檔案的語法／ESLint 檢查及以下案例，沒有執行全套遊戲驗證。

```sh
node --test tests/pixel-mobile-planner.test.mjs
npx playwright test pixel-mobile-controls.spec.mjs --project=mobile --project=mobile-webkit --workers=2 --reporter=line
```

瀏覽器案例使用 390 × 844 手機尺寸，檢查：

1. 不重新捲動、不重新定位，用同一螢幕座標連點八次，確認依序排入週一至週日且不繞回；展開助手、活動篩選、畫面位置均保留。
2. 手動選回星期二並改成另一堂課，其餘日期保持原安排。
3. 週中連排略過正式約定，保留已完成日期；未開放活動保持停用。
4. 場景放大、縮小後分別從設定與場景按鈕還原，確認日期、金錢、行程不變。
5. Chromium 手機頁面設為 200%／150%，確認浮動按鈕仍在可視範圍內且可以點選；還原為 100% 後，viewport 原設定及行程捲動位置保留，並可再次放大。

頁面縮放案例使用 Chromium 的實際頁面縮放模擬。WebKit 案例涵蓋連點、捲動、約定保留和場景鏡頭；不宣稱已使用實體 iPhone 測試雙指手勢。

## 瀏覽器實作依據與限制

`VisualViewport.scale` 是唯讀值，浮動按鈕依可視範圍的位移與倍率定位，參考 [MDN VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport)。動態 viewport 還原的相容性背景見 [CSSWG 討論 #9787](https://github.com/w3c/csswg-drafts/issues/9787)。

若瀏覽器或使用者的輔助使用設定拒絕頁面還原，保留按鈕並顯示實際狀態，不宣稱頁面已成功還原。桌面瀏覽器選單控制的整頁縮放、作業系統放大鏡不屬於網頁可控制的倍率。
