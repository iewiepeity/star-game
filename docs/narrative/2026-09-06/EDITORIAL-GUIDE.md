# 《星途未定》文本編輯總綱

版本：2026-09-06。適用對象：像素版共用文本的編劇、編輯與整合工程師。

本文記錄本次改稿採用的敘事規則、角色定位與程式入口。原文備份、替換清單與驗證結果由同目錄的其他備查文件管理；本文不代替變更紀錄，也不宣稱每一則文字都具有獨立的永久分支系統。

## 1. 敘事中心與不可擅改的起點

玩家大學畢業後來到星望市，給自己五年嘗試演藝生涯。年齡由既有引擎以 22 歲起算。童年卡片、搬家紙箱、空白履歷與五年之約是共同開場；職業方向、經紀公司、作品成績與重要關係必須在遊戲裡逐步形成。

演藝工作是具體的準備、合作與交付：歌曲要處理聲音和情緒，影視要處理人物動機與連戲，綜藝要處理規則、節奏與來賓反應，廣告要處理形象、產品訊息及合作範圍。不要讓所有工作只剩「很緊張，努力後獲得掌聲」。

趣味主要來自角色的觀察、職業習慣及小小失誤；戀愛主要來自誰記得細節、誰願意說清楚需要，以及工作之外如何相處。專業人物也可以嘴硬、失落、說錯話；不是每次出場都要講一段職涯道理。

養成結果容許不成名、作品普通、拒絕工作、保持朋友、獨自生活與提早離開。不得替低成績玩家補寫爆紅，不得把未交往的信任當成告白，不得把自由身玩家的決定寫成「公司已替你安排」。

## 2. 五年主題與回收位置

一年為 52 週。年度章節起點為第 1、53、105、157、209 週；五年總長 260 週。章節名稱保留既有資料鍵與呈現名稱。

| 年度 | 主題 | 當年的具體問題 | 後文如何接續 |
| --- | --- | --- | --- |
| 第一年：活下來 | 生活與嘗試共存 | 房租、零工、課程、休息如何放入同一張表 | 第二年引用第一年的實際選擇；履歷仍空白時如實承認 |
| 第二年：我是誰 | 用半年試方向 | 影視、音樂、主持綜藝、商業形象擇一專注 | 依既有承諾限制三星以上的其他路線；基礎工作仍可進行 |
| 第三年：位置有限 | 決定怎麼與他人競爭 | 正面競爭、合作聯盟、獨特定位 | 各自累積聲勢、可信度或業界評價；獨特定位排除四星以上廣告 |
| 第四年：選擇有代價 | 把工作界線寫清楚 | 商業資源、創作自主、能長久維持的作息 | 商業路線有固定收入；自主排除三星以上廣告；持續路線最多並行兩份正式合約並恢復身體 |
| 第五年：留下什麼 | 為五年之約收尾 | 代表作、重要關係、傳承或整合生活 | 依實際作品、方針與關係判定結局；選定目標本身不等於已達成 |

年度文字由目前作品、前一年事件紀錄與經紀狀態組成。方針回響每種有兩個不同情境，依既有出現紀錄交替。它們呈現取捨，不另行暗示尚未實作的邀約、道具或好感收益。

終局保留 19 個既有 `endingId` 與判定優先序。正文從封存快照讀取作品與關係，不拿即時狀態改寫已結束的人生。提早退圈使用實際週數；死亡使用獨立收束，不接「休息後繼續挑戰」的普通尾段。結局圖的名稱不代表每個玩家都真的走過圖中的紅毯或典禮。

### 可攻略範圍與關係進度

主要人物中，除秦紹謙外的九人具有一般或條件式戀愛路線。宋知夏、裴硯之、黎曼青屬條件式；周予珩也有已完成作品的前提。具體門檻以 `src/data/romance.js` 與 `src/logic/romance-engine.js` 為準，不靠角色台詞自行解鎖。

裴硯之、周予珩、黎曼青、宋知夏、溫時嶼存在直接工作衝突檢查。拒絕私人邀請不得寫成損失選角機會；數值未通過前，不用一句「你已經獨立了」取代資格判斷。

關係依序為：尚未定義、開始在意、曖昧、交往、穩定伴侶、訂婚、婚姻。告白接受後才開始交往；訂婚與結婚不能提前藏進前段回憶。早期拒絕會留下拒絕狀態；交往後暫緩更大承諾，不等於分手。被拒絕或分手後重新接近，先回到了解彼此的階段，不直接恢復舊伴侶位置。

秦紹謙的路線是 `disabled`。相容資料仍可能保留以戀愛階段命名的欄位，這些欄位的存在不構成可攻略證據。其實際文字維持朋友與職涯夥伴，不寫訂婚、婚姻、佔有式承諾或用合約交換親密。

現行引擎結婚後婚訊為公開狀態。「只邀親友的婚禮」表示儀式與細節私密，不等於引擎提供秘密婚姻分支。台詞與選項提示須清楚區分。

### 沈霧棠的特殊位置

`silver_pc`／沈霧棠是動態影像設計師、動態捕捉演員，另有第二周目起的八章特殊人物線。她不計入上述九位一般可攻略人物；一般戀愛引擎仍將其標記為 `hidden`，不能宣稱八章結束便自動開放訂婚或結婚。

相似夢境是未能驗證的線索，不是今輪的作品、獎項或戀愛紀錄。八章圍繞不同分鏡、《第九秒以後》與未知九秒素材展開；刪除副本與封存會留下不同的資訊代價，選朋友後的末章仍是朋友。接近、宵夜與道別不暗中修改伴侶狀態。

## 4. 分支的五段結構

每個有後續的分支先填完下表，再接程式。此表是交稿規格，不代表每類隨機小事都必須新增延遲事件。

| 段落 | 交稿必須具體寫出什麼 | 接入位置與查核方式 |
| --- | --- | --- |
| 前提 | 現在在哪裡、誰在場、哪件事尚未決定；需要的作品、關係、時間或旗標 | 對照 `requires`、關係階段、工作紀錄及像素場景表；未滿足的事只能是提案或猜測 |
| 選擇 | 玩家現在真的能做的兩至三種行動 | 使用現有選擇 ID；不要一個選項寫處理方式，另一個只寫人格評價 |
| 代價 | 誰要多做工作、放棄何種機會、資訊是否仍未知；當下結果到哪裡為止 | 對照 `effect`／`effects`。文中的收入、好感、完成作品與場次必須和引擎相符 |
| 延遲 | 多久以後、依哪個分支旗標或紀錄出現哪一份消息 | 使用選項自己的 `followUp`，或該類既有排程器；排入佇列不等於已讀或已完成 |
| 回收 | 前次選擇如何改變現在，而未採用的做法仍造成什麼缺口 | 讀取真正的 `eventHistory.choice`、旗標或作品結果；只回收被選中的路，不能兩種成果一起出現 |

目前已用到的回收方式各不相同：

- NPC 三章主線引用上一章實際選擇；下一章需有前章完成紀錄。
- 人物長篇的兩選擇具有不同的延遲文字與結果；由長篇事件整合層接上既有延遲流程。
- 多人合作場景的三種選擇各有三週後確認稿；支持其中一方不寫成所有人同時最滿意。
- 短事件鏈以原旗標連接六週後回收。各種訓練／地點小事若沒有後續欄位，不寫「下週一定有人來找你」。
- 職涯方針依既有週期持續生效，回響只呈現取捨；隱藏線則讀上一章選項補入後果。
- 原創發行文字依真實 `marketScore` 分檔；續作完成文字依 `quality` 與是否加價分檔。保持「市場反應」與「作品品質」是兩個可不同的答案。

以沈霧棠的素材分支為例：刪除後，手上的副本不能再拿來重播，未知仍然存在；封存後，可保留以後查證的可能，但尚未變成可信證據。後續宣傳不能忽然引用副本替命定關係作證。這是已存在的文本回收，不是新增檔案管理玩法。

## 5. 像素演出的交稿尺度

以下是後續編輯與增修的尺度，並非引擎現有的強制字數上限，也不表示所有本次稿件都已套用同一個長度。

| 單位 | 建議尺度 | 寫法 |
| --- | --- | --- |
| 每幕 `beats[].text` | 約 60–140 個中文字；必要前因可更長 | 一個可辨認的動作或談話轉折，一次不要跨過多天或多個場景 |
| 事件總述 `text` | 約 80–180 字；歷史回聲另外接入 | 交代當下矛盾，不先宣布玩家選哪一邊 |
| 選項 `label` | 約 8–24 字 | 動詞開頭，讓玩家知道按下去會做什麼 |
| 結果 `outcome` | 約 60–150 字 | 具體回應當次行動，留下差別；不要重貼整段事件總述 |
| 日常訊息／動態 | 約 25–90 字 | 像角色真的會傳的訊息，可有停頓與短句 |
| 終局正文 | 可長於一般事件，分段收束 | 實際作品、方針、關係與生活狀態各自有功能，不變成重複評分表 |

人物章節通常以三幕承接；像素層也可能插入含前分支資訊的總述，因此資料有三幕不保證畫面永遠恰好三頁。不要為湊頁數抹去回聲，也不要在每一幕都重複完整前情。

`cast`、`npcId` 與 `speaker` 需要對得上實際人物。像素演出依 `CHAPTER_SETS`、`HIDDEN_CHAPTER_SETS` 與其他既有場景映射找房間；文字改到另一場所時，要同時核對映射。沒有新增房間時，不把新地名寫成已能在地圖前往的功能。場內提起外地往事與真的切換場景須分清楚。

圖說只描述本章能成立的場面。不要因為共用 CG 看起來像首映，便把玩家寫成已主演電影；不要在尚未選擇時把 CG 標題寫成某一分支已經成功。修改圖說不等於修改圖檔內容，路徑與 ID 分開維護。

## 6. 玩家身分、時間與文字習慣

- 玩家性別、外貌、姓名與職涯方向可由遊戲選擇。專業對話可以談表演，但沒有作品或工作前提時，不直接稱玩家影帝、主唱、主持人或對手戲演員。
- 本名與藝名依既有姓名工具和場景用途讀取；私下稱呼不憑空發明第三個名字。玩家可以用本名，不要寫「你終於放下藝名」這種必須有藝名才成立的句子。
- 玩家可以分享觀察、陪讀或協助想方案，這不會自動取得正式劇組職位、原創署名、收入或作品紀錄。
- 不替玩家寫長篇固定價值宣言。情緒可由場景誘發，承諾與方向由選項確認；同一幕須容得下想留下、想拒絕、還沒想好的人。
- 提案、試鏡通過、簽約、開工、完成、發行、入圍、得獎是不同時點。知道有一份邀約，不等於已排入行程；結算過收益，才把該收益寫成已取得。
- 使用台灣繁體中文與全形標點。職業常用語保持自然，如「通告、試錄、排練、讀本、收工、邀約、班表、訊息」。角色可口語吐槽，不用每句加網路流行語。
- 好感的具體數值是引擎判斷資料，不在角色台詞中報點數。文案提示若需要說明限制，精確列出已實作條件，不用不存在的獎勵美化選項。

## 7. ID、快照與替換紀錄

1. 純文本改稿保留人物、通告、章節、選項與結局 ID；旗標名稱也視為相容介面。舊鍵看起來與新標題不一致時，保留鍵，修正顯示文字與圖說。
2. `eventHistory` 裡已完成事件的選項、結果與效果是當時的人生紀錄，不以新版正文直接覆蓋。章節進度不能只憑「曾排隊」便當成玩家已作出選擇。
3. 已產生的 `endingSnapshot` 與 `endingResult` 不因玩家開啟新版而重寫；新的結局使用新的正文組裝。新增快照欄位需容許舊快照沒有該欄位，不能把缺資料一律解讀成自由身或疲憊。
4. 若為相容性更新尚未完成的事件呈現，例如現有隱藏線／邀約的顯示適配器，保留原事件 ID、選擇 ID、效果、條件與已結算紀錄。重繪場景不得再次發放效果。
5. 像素 `storyStage` 是呈現位置。讀檔時可以重新取得場景配置並校正閱讀位置，但不能因為舊呈現停在選項前，就重演已完成的選擇。
6. 每次替換要能定位舊來源、舊鍵與新來源；保留原文備份／差異及替換理由。新增作者稿接進舊模組時，須說清楚哪個來源是真正執行中的正文，不能只新增檔案卻讓遊戲仍讀舊稿。
7. 保留舊格式是相容需求，不表示需要把過期敘事繼續複製進新場景。相容讀取、玩家已發生的記錄、新發生的故事，分別查核。

## 9. 交付時必須能回答的五個問題

1. 一個零作品、自由身、沒有伴侶的玩家，是否仍能合理讀完此稿？若不能，資格在哪裡限制？
2. 選另一邊之後，下一場會讀到哪一份文字？那份文字是否仍錯用被放棄的成果？
3. 文中新增的報酬、檔期、作品、關係或邀約，究竟已由哪個既有流程建立？若沒有，就改寫成意圖、提案或尚未決定。
4. 玩家在像素版會在哪間房、與誰讀到這一幕？是否只是改了資料檔，卻被另一個顯示分支覆蓋？
5. 替換的原文與舊鍵在哪裡可查？既有存檔中已完成的選擇，是否仍保持當時的樣子？

上述問題各自對應可查的資料或呼叫位置。答不出來時，先補前提、改寫成果或完成接入；不要只在文件上標示「具蝴蝶效應」。
